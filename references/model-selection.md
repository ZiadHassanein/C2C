# Research and select worker models

Apply this policy to **each new planning task with a candidate route** and explicit model-advice requests. Include [execution advice](#recommend-models-for-execution) in the delivered plan. Either app may initiate; do not change that chat or global configuration. Follow [route selection](protocol.md#choose-an-available-route): availability candidates first, then research, exact host identity/roles, and finally launch eligibility for the required workers. Unknown billing metadata is not a reason to skip candidate research. Prefer cross-provider; preserve explicit model/provider limits and the existing same-provider fallback. Do not research known inaccessible workers, force setup or claim unverified eligibility.

## Research once per task

Search current official guidance for providers in the **candidate route** (both OpenAI and Claude for cross-provider planning), using concise task-fit terms without private project details. Open relevant pages; snippets and remembered rankings are insufficient. Establish date, full IDs, suitability for the task's planning, coding, writing, editing or visual needs, constraints and reasoning settings. Research can establish suitable choices before their billing eligibility is known; it authorizes no launch. Reuse this task's evidence across stages and a permitted route transition; research only newly needed candidates.

Read relevant catalog and task-fit sections, then expand only to resolve material uncertainty about suitability, identity or access. Save concise conclusions and links instead of copied catalogs or full articles. Freshness does not require repeating the same research at every stage.

Use `node RUNNER guide --topic models` to load the applicable local policy sections, adding `--run RUN` for a prepared run's pinned instructions. Reuse policy already read; this local command does not replace fresh provider research or establish model access.

Start with relevant provider selection/catalog pages: [OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection), [Codex models](https://learn.chatgpt.com/docs/models), [Claude selection](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model), [Claude catalog](https://platform.claude.com/docs/en/models/overview), and [Claude Code configuration](https://code.claude.com/docs/en/model-config). Add task-specific official guidance, such as [OpenAI coding guidance](https://developers.openai.com/api/docs/guides/code-generation) for software or writing/vision guidance for content. No model family is a permanent winner. A coding ranking does not establish writing or editorial suitability; general-purpose models can lead both roles. Visual capability in a catalog does not give C2C's text-only workers image access.

Write a compact matrix in `TASK_ASSESSMENT.md`: provider, strongest suitable planning candidate, task-fit critic candidate, task-fit reason, exact IDs, dated sources, and access/limit evidence. Keep the full research log and worker-selection details out of peer packets; only the compact execution recommendation and supporting assumptions enter the final plan for verification. If fresh research is unavailable, record the gap; never describe cached guidance as freshly verified. Do not launch a newly inferred pair from stale rankings. Preserve useful discovery and identify the missing source/access evidence; explicit user-selected models or already verified choices within this task remain usable within their limits.

## Filter before choosing

Match scope, ambiguity, risk, context, quality, latency and usage constraints. Use read-only model metadata to support candidate selection. [Codex `model/list`](https://learn.chatgpt.com/docs/app-server) supplies catalog/capability evidence, not the current chat's identity or unconditional entitlement. Claude's picker and managed policy can limit or substitute choices. API model access does not establish subscription CLI access. Do not read credentials or make selection probes.

Use canonical versioned IDs. Modern Claude dateless IDs can be fixed snapshots; older short IDs can be aliases. Resolve identity using [versioning guidance](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions). Different effort levels, aliases, or context variants of one model do not establish distinct participants.

## Assign real roles

- **Cross provider:** select the best task-fit planning worker available within limits from each provider. Both evaluate feasibility, relevant security and acceptance checks.
- **Same provider, explicitly chosen or availability fallback:** select a planning author and a distinct task-fit critic. Use a coding critic for software; an editorial/factual critic for content, considering audience, structure, language/tone, source support and media descriptions; and both perspectives within the same critic role for mixed work. The critic challenges consequential choices and verification. If the strongest planner and critic overlap, disclose that and select the strongest adequate distinct alternative without claiming it is the absolute best. If no adequate distinct eligible option exists, use a labeled solo self-critique instead of claiming two-model review.
- Automatic worker selection within the requested limits is authorized. Exact choices and advice-only instructions override it. Do not repeat permission questions for eligible choices; resolve only genuinely missing facts or authority.

Before deciding whether an author worker is needed, check [this chat's exact identity](protocol.md#pairing-and-model-identity) through trustworthy current-session metadata. If it matches the researched planner, reuse the host and check only the peer CLI's launch eligibility. Otherwise select `--author-model` plus `--peer-model` and check all required worker providers. Selection is not launch permission: apply the [bounded usage checks](protocol.md#no-paid-limit-recovery), including strict no-overflow evidence when required, before any call. Do not gate the host-author route on an unused CLI, guess identity or assume a background author qualifies. Keep host, requested and reported identities distinct.

Apply the user's actual [billing policy](protocol.md#no-paid-limit-recovery) to those workers. For normal authorized subscription use, combine selected CLI route metadata with current model/plan guidance and relevant user reports; live quota can remain unknown. Catalog access is supporting evidence, not a promise of success. A hard included-only/zero-extra-charge constraint, including equivalent prohibitions on paid-credit consumption, still requires applicable no-overflow evidence. Follow the bounded supported check before declaring that evidence unavailable; if it remains missing, do not launch. Do not require fresh billing confirmation merely because purchases and paid recovery are forbidden. API/cloud credentials never grant metered authorization by their presence.

Exclude models outside the authorized billing scope. [Claude Fable in non-interactive mode](https://code.claude.com/docs/en/model-config#fable-and-usage-credits) may consume additional credits without a consent prompt; exclude credit-only choices on subscription/no-extra-charge routes. Worker fast mode stays disabled. Runtime/attempt ceilings are not spending caps. Do not make access probes, assume a CLI will ask before charging, solicit purchases, change accounts or enable credits.

The host-author route needs two successful calls for review or three for plan. A background author needs three for review or five for plan, including the author's critique. Background-author plan mode defaults to six attempts unless explicitly capped. Record the route and limits; announce participants once and discuss operational limits only when requested or consequential, following [visible discussion](protocol.md#visible-discussion). Separate real reports supply the arguments; neither forced agreement nor invented objections improves review.

If the other provider is blocked before preparation, automatically consider an eligible pair in the initiating provider. After a run starts, follow the [single bounded route transition](protocol.md#change-route-after-a-worker-block), or deliver provisional planning. Do not probe replacement models inside the blocked provider, relabel the chat, change sealed identities or treat different models as separate account quotas. If the initiating provider itself is blocked, its other models are not an assumed escape route. User instructions to require both participants or wait override fallback.

## Recommend models for execution

Recommend who should carry out the first work item, separately from who planned or reviewed it. These are **advisory choices**: automatic selection of planning workers is not permission to switch the host, build, produce or publish content, change settings or enable spending. Honor pinned execution choices. Reuse this task's official research; refresh only missing or changed execution facts. For provisional work, use known current-chat capabilities or record the advice gap without blocking the plan or researching inaccessible workers.

Match the bounded work, risk, ambiguity, source context, required tools and acceptance gates. Recommend the best suitable eligible model/effort and, when justified, one lower-cost alternative. A clear mechanical edit may suit an efficient model; unfamiliar architecture, difficult diagnosis, complex source synthesis or sensitive claims may warrant stronger capability. For content, assess writing, editing, language and visual requirements instead of defaulting to the best coder; identify the tools and actual media access needed for later visual work. Size alone does not decide. Describe lower-cost options as conditional until their quality is supported; retain security and acceptance gates. Effort advice is not a runner flag or an automatic downgrade of planning/review depth.

**Explain the choice before showing a percentage.** Connect a concrete task fact to relevant documented capability or observed evidence, then explain why this model is preferred over the alternative for this scope. Name the tradeoff: what the alternative could handle, what remains unproven, and what failure or change would justify reconsideration. “Best”, “smarter” or “cheaper” alone is not a rationale; a higher price does not establish better task results. Keep this to a few decision-focused sentences for a small feature.

Explain the cause of any supported saving too: lower published rates for the same token categories, or a measured usage difference with its observed cause and limits. Do not invent fewer reasoning tokens, fewer retries, smaller model size or hidden architecture from a price table. If actual usage/quality is unknown, say why the recommendation is still a reasonable candidate and which acceptance check will test that judgment.

Use current official model/configuration and pricing pages for identities, tools, access and rates. Add one focused search for relevant firsthand community experiments or social reports; open only useful sources. Record source date, exact tested models, task/setup and limitations. A reproducible comparison is stronger than an anecdote; votes, promotional claims and old-model rankings do not establish today's winner. Label inference and conflicting evidence. If browsing or useful community evidence is unavailable, disclose that once and continue with supported guidance. Search with generic task-fit terms, never private project details.

For rates, distinguish [OpenAI API pricing](https://developers.openai.com/api/docs/pricing), [Codex plan usage](https://learn.chatgpt.com/docs/pricing), [Claude API pricing](https://platform.claude.com/docs/en/about-claude/pricing) and [Claude Code usage](https://code.claude.com/docs/en/costs). Include relevant rates and assumptions in a numeric recommendation; the verifier can check supplied arithmetic and rationale, but cannot open source links or independently verify the research.

Keep source details in `TASK_ASSESSMENT.md`. Before verification, put a compact **Execution model recommendation** beside Start here: scope, primary model and supported effort, decisive reason, adequate alternative or none, eligibility/confidence, and the failed check or complexity change that would justify reconsideration. For roadmaps, add rows only where milestones materially differ; future choices remain provisional. Show dated source links and these distinct savings labels:

- **Task tokens:** a percentage needs compatible whole-task measurements for the same task and acceptance bar, counting input/output, reasoning without double counting, tool context and retries. State baseline, candidate, sample/setup and quality outcome. Third-party results apply to their experiment only; they are not a forecast for this project. Otherwise say **unknown — no matched measurement**.
- **API price estimate:** if useful, compare dated official rates for an explicit equal token mix and matching service tier/context/cache assumptions. Use `100 × (baseline cost − candidate cost) / baseline cost` for a positive baseline, retaining negative results. Calculate each token category separately; include applicable fees or identify exclusions. Label it **equal-token API price estimate**, never token reduction or measured task savings. If only category rates are known, compare those categories without inventing a total.
- **Subscription allowance:** unknown unless applicable provider evidence or matched account observations establish it. API prices, credit tables, message ranges and social reports do not establish an included-allowance percentage or authorize extra credits.

Do not invent a percentage, average incompatible studies, add savings percentages together or guarantee unchanged performance. Missing metrics stay unknown. No paid benchmark/probe is needed to produce advice. Compare complete successful-task effort when evidence exists; a cheaper request that needs more retries may cost more overall. See [measurement rules](https://github.com/ZiadHassanein/C2C/blob/main/docs/BENCHMARKS.md#execution-model-estimates).

`node RUNNER usage --run RUN` exposes observed worker terminal usage and counter subtotals with missing/partial/ambiguous observations explicit. It does not measure the coordinator's research, reasoning or synthesis, or all provider-internal work. Unknown counters remain unknown; cache and reasoning subsets are not additional totals. Use this as scoped observation, never a whole-task saving, subscription-cost estimate, remaining-allowance check or reason to weaken review. See the [usage scope and context-profile limits](protocol.md#token-efficiency).
