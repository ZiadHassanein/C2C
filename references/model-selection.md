# Research and select worker models

Apply this policy to **each new worker-backed planning task** and explicit model-advice requests. Include [execution advice](#recommend-models-for-execution) in the delivered plan. Either Codex or Claude Code can be the initiating chat; worker selection never changes that chat or global configuration. Honor exact selections, advice-only requests, provider preferences and limits. Check [route eligibility](protocol.md#choose-an-available-route) first: prefer cross-provider, otherwise automatically select a planner and distinct coding critic in the available initiating provider. If no eligible pair exists, use provisional planning with an honest self-critique. Do not research or probe inaccessible workers, force setup or imply skipped recommendations were verified.

## Research once per task

Search current official guidance for providers in the eligible route (**both OpenAI and Claude** for cross-provider planning), using concise task-fit terms without private project details. Open relevant pages; snippets and remembered rankings are insufficient. Establish date, current full IDs, planning/coding suitability, constraints and available reasoning settings. Reuse this task's evidence across stages and a bounded route transition; research only newly needed candidates. A new worker-backed task needs a fresh search.

Read relevant catalog and task-fit sections, then expand only to resolve material uncertainty about suitability, identity or access. Save concise conclusions and links instead of copied catalogs or full articles. Freshness does not require repeating the same research at every stage.

Start with [OpenAI model selection](https://developers.openai.com/api/docs/guides/model-selection), [Codex models](https://learn.chatgpt.com/docs/models), [OpenAI coding guidance](https://developers.openai.com/api/docs/guides/code-generation), [Claude selection](https://platform.claude.com/docs/en/about-claude/models/choosing-a-model), [Claude catalog](https://platform.claude.com/docs/en/models/overview), and [Claude Code configuration](https://code.claude.com/docs/en/model-config). No model family is a permanent winner. A coding suffix does not prove superiority; general-purpose models can lead both roles.

Write a compact matrix in `TASK_ASSESSMENT.md`: provider, strongest suitable planning candidate, coding/review candidate, task-fit reason, exact IDs, dated sources, and access/limit evidence. Keep the full research log and worker-selection details out of peer packets; only the compact execution recommendation and supporting assumptions enter the final plan for verification. If fresh research is unavailable, record the gap; never describe cached guidance as freshly verified. Do not launch a newly inferred pair from stale rankings. Preserve useful discovery and identify the missing source/access evidence; explicit user-selected models or already verified choices within this task remain usable within their limits.

## Filter before choosing

Match scope, ambiguity, risk, context, quality, latency, and usage constraints. Check read-only local metadata for the actual worker route. [Codex `model/list`](https://learn.chatgpt.com/docs/app-server) supplies catalog/capability evidence; catalogs are not unconditional entitlement proof. Claude's picker and managed policy can limit or substitute choices. API model access does not establish subscription CLI access. Do not read credentials or make paid selection probes.

Use canonical versioned IDs. Modern Claude dateless IDs can be fixed snapshots; older short IDs can be aliases. Resolve identity using [versioning guidance](https://platform.claude.com/docs/en/about-claude/models/model-ids-and-versions). Different effort levels, aliases, or context variants of one model do not establish distinct participants.

Exclude models outside the known authorized billing scope. In particular, [Claude Fable in non-interactive mode](https://code.claude.com/docs/en/model-config#fable-and-usage-credits) may bill additional usage credits without a consent prompt. Runtime/attempt ceilings are not spending caps. Do not enable credits, change accounts, or assume a CLI will request permission.

When the user forbids extra spending, a saved login or available API key is not permission to use paid credits, overage or API/cloud billing. Establish that the selected credential/model fits the authorized allowance using available read-only evidence or existing user confirmation; never inspect secret values or make a paid access probe. If included-only eligibility remains unknown, preserve useful planning through the [billing-boundary fallback](protocol.md#no-paid-limit-recovery), rather than assuming the call is free. Do not solicit purchases or upgrades to unblock a council.

## Assign real roles

- **Cross provider:** select the best task-fit planning worker available within limits from each provider. Both evaluate feasibility, security, and tests.
- **Same provider, explicitly chosen or availability fallback:** select a planning author and a distinct coding-focused critic. The critic challenges implementation details, failure cases, security and verification; it does not rubber-stamp the plan. If the strongest planner and coder overlap, disclose that and select the strongest adequate distinct alternative; do not falsely call it the absolute best coder. If no adequate distinct eligible option exists, use a labeled solo self-critique instead of claiming two-model review.
- Automatic worker selection within the requested limits is authorized. Exact choices and advice-only instructions override it. Do not repeat permission questions for eligible choices; resolve only genuinely missing facts or authority.

Use `--author-model` for a background planning author from the coordinator's provider and `--peer-model` for the other participant. Reuse the host as author only when trustworthy metadata exactly matches the selected planner. Otherwise launch the selected background author; do not guess or unnecessarily ask for the chat's identity. Keep role, requested identity, and reported identity distinct.

The host-author route needs two successful calls for review or three for plan. A background author needs three for review or five for plan, including the author's critique. Background-author plan mode defaults to six attempts unless explicitly capped. Announce the chosen route and limits before execution. Separate real reports supply the arguments; neither forced agreement nor invented objections improves review.

If the other provider is blocked before preparation, automatically consider an eligible pair in the initiating provider. After a run starts, follow the [single bounded route transition](protocol.md#change-route-after-a-worker-block), or deliver provisional planning. Do not probe replacement models inside the blocked provider, relabel the chat, change sealed identities or treat different models as separate account quotas. If the initiating provider itself is blocked, its other models are not an assumed escape route. User instructions to require both participants or wait override fallback.

## Recommend models for execution

Recommend who should implement the first work item, separately from who planned or reviewed it. These are **advisory choices**: automatic selection of planning workers is not permission to switch the host, launch implementation, change settings or enable spending. Honor pinned execution choices. Reuse this task's official research; refresh only missing or changed execution facts. For provisional work, use known current-chat capabilities or record the advice gap without blocking the plan or researching inaccessible workers.

Match the bounded work, risk, ambiguity, repository context, required tools and acceptance gates. Recommend the best suitable eligible model/effort and, when justified, one lower-cost alternative. A clear mechanical edit may suit an efficient model; unfamiliar architecture, authorization, migrations or difficult diagnosis may warrant stronger capability. Size alone does not decide. Describe lower-cost options as conditional until their quality is supported; retain security and acceptance gates. Effort advice is not a runner flag or an automatic downgrade of planning/review depth.

Use current official model/configuration and pricing pages for identities, tools, access and rates. Add one focused search for relevant firsthand community experiments or social reports; open only useful sources. Record source date, exact tested models, task/setup and limitations. A reproducible comparison is stronger than an anecdote; votes, promotional claims and old-model rankings do not establish today's winner. Label inference and conflicting evidence. If browsing or useful community evidence is unavailable, disclose that once and continue with supported guidance. Search with generic task-fit terms, never private project details.

For rates, distinguish [OpenAI API pricing](https://developers.openai.com/api/docs/pricing), [Codex plan usage](https://learn.chatgpt.com/docs/pricing), [Claude API pricing](https://platform.claude.com/docs/en/about-claude/pricing) and [Claude Code usage](https://code.claude.com/docs/en/costs). Include relevant rates and assumptions in a numeric recommendation; the verifier can check supplied arithmetic and rationale, but cannot open source links or independently verify the research.

Keep source details in `TASK_ASSESSMENT.md`. Before verification, put a compact **Execution model recommendation** beside Start here: scope, primary model and supported effort, decisive reason, adequate alternative or none, eligibility/confidence, and the failed check or complexity change that would justify reconsideration. For roadmaps, add rows only where milestones materially differ; future choices remain provisional. Show dated source links and these distinct savings labels:

- **Task tokens:** a percentage needs compatible whole-task measurements for the same task and acceptance bar, counting input/output, reasoning without double counting, tool context and retries. State baseline, candidate, sample/setup and quality outcome. Third-party results apply to their experiment only; they are not a forecast for this project. Otherwise say **unknown — no matched measurement**.
- **API price estimate:** if useful, compare dated official rates for an explicit equal token mix and matching service tier/context/cache assumptions. Use `100 × (baseline cost − candidate cost) / baseline cost` for a positive baseline, retaining negative results. Calculate each token category separately; include applicable fees or identify exclusions. Label it **equal-token API price estimate**, never token reduction or measured task savings. If only category rates are known, compare those categories without inventing a total.
- **Subscription allowance:** unknown unless applicable provider evidence or matched account observations establish it. API prices, credit tables, message ranges and social reports do not establish an included-allowance percentage or authorize extra credits.

Do not invent a percentage, average incompatible studies, add savings percentages together or guarantee unchanged performance. Missing metrics stay unknown. No paid benchmark/probe is needed to produce advice. Compare complete successful-task effort when evidence exists; a cheaper request that needs more retries may cost more overall. See [measurement rules](../docs/BENCHMARKS.md#execution-model-estimates).
